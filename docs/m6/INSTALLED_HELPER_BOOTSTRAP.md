# Privileged helper bootstrap contract

The build produces `llm_interceptor_helper`, a separate command-line executable. Its `--check-state-dir` mode performs a read-only state-directory check and exits. The `--process --state-dir PATH --bootstrap-fd FD` entrypoint validates the root-owned private directory, then deliberately exits with `production_peer_authenticator_unavailable` (code 5). It does not read the supplied descriptor, start a host, open a control socket, or mutate PF or ARP. Do not load it as a persistent launchd service or claim the installed-helper gate is met yet.

`InstalledHelperProcessBootstrap::create` is the injectable process seam: it opens and retains the private state-directory descriptor, authenticates and receives the handoff on one connected Unix socket, derives kernel UID/GID credentials from that same socket, and calls `LeasedHelperHost::createFromBootstrap`. It exposes explicit host start and one-time credentials retrieval. Its injected operations factory is responsible for the mandatory fresh pre-mutation gate; the production executable does not instantiate this seam until a production authenticator and gated backend are available. The factory must wipe any secret copy it retains. The transferred snapshot cannot recheck GUI-owned listener readiness. This seam does not install a service, create the GUI/helper rendezvous, or provide a live backend.

`MacXpcPeerCodeSignaturePolicy` asks Security.framework to resolve the sender from the message's kernel-associated audit token and validates the code against an explicit code requirement. `XpcControlRequestGate` pins a copy of that requirement at construction and authenticates each actual inbound message before parsing. It accepts only a single `operation` string with value `probe` or `status`. `XpcReadOnlyControlAdapter` returns fixed bounded probe/status replies, and `XpcReadOnlyServiceListener` provides a native event-listener foundation with peer and request limits.

The helper also has an opt-in `--mach-service --state-dir PATH` mode. It remains root-gated and requires `mach-service.conf` inside the already validated root-owned `0700` state directory. The config file must be a root-owned regular file with exact mode `0600`, opened relative to the validated directory descriptor without following symlinks. Its strict format is exactly two ordered lines (an optional final newline is allowed):

```text
enabled=false
peer-code-requirement=anchor apple
```

The disabled example uses a parser fixture and fails closed. Enabled configurations require a single literal `cdhash H"…"` matching the identity preview format, with exactly 40 or 64 ASCII hexadecimal digits and no extra whitespace or clauses. The literal must also compile as a Security.framework code requirement. The service name is fixed as `org.local-llm-interceptor.helper`; it cannot come from config, the GUI, or an XPC message. A local administrator must replace the example requirement with the reviewed identity of the signed GUI client and explicitly set `enabled=true`. No Developer ID identity is available in this checkout, so no usable production identity is bundled.

`mach_service_identity_preview --app /absolute/path/to/llm_interceptor.app` is a read-only way to prepare the peer requirement for review. It accepts only the expected app bundle and executable path, runs `/usr/bin/codesign --verify --strict --deep`, and reads a single literal `designated => cdhash H"…"` requirement from `codesign -d -r-`. Any signature error, timeout, excess output, unexpected output, alternate requirement form, symlinked bundle component, or identity/path mismatch fails closed. The preview records the executable’s filesystem device, inode, size, content modification time (mtime), and status change time (ctime) before the first `codesign` call. After each successful call it compares those values, including the nanosecond components of both timestamps, and rejects detected changes or unavailable metadata. These checks are point-in-time observations. They can miss transient replacements between checks and only track the executable’s metadata. Before printing a proposal, the preview uses the enabled helper’s literal cdhash gate to compile the requirement with local Security.framework. If compilation fails, it exits with `exact_cdhash_requirement_unavailable` and leaves standard output empty. The preview then runs `codesign --verify --strict --deep -R=<exact cdhash requirement>` on the same bundle to confirm that the requirement matches. A timeout or verification failure returns `codesign_requirement_verification_timed_out` or `codesign_requirement_verification_failed` with empty standard output. On success, standard output is exactly the two-line config format above, with `enabled=false`; redirecting it is optional and is the user's own file operation. The tool does not create a file, change permissions, install or enable the helper, or alter system configuration. This is an advisory review aid: strict verification checks code integrity and does not identify or vouch for a publisher, while a cdhash only pins the exact executable bytes. With no Developer ID/team identity available, the administrator must trust the selected review build and independently establish its provenance. Before enabling any separately provisioned config, reverify the signature and exact cdhash of the app at installation against the reviewed build. The current linker ad-hoc debug app may fail strict bundle verification; do not weaken this check to make it pass. Use a fully valid, locally signed review build. The cdhash changes whenever the app executable is rebuilt or re-signed, so generate and review a fresh proposal for each exact build that will be installed. The proposal never enables the service and still requires administrator review of the exact installed build.

To create a separately signed review copy of the GUI bundle and immediately preview its disabled identity proposal, use the non-installing staging script after building the app and preview tool:

```sh
python3 scripts/stage_signed_gui_review.py \
  --app "$PWD/build/debug/llm_interceptor.app" \
  --output-dir /private/tmp/llm-interceptor-gui-review
```

The script copies the app to `llm_interceptor.app` inside a new or empty absolute review directory, removes extended attributes only from that staged copy, applies an ad-hoc signature, runs strict/deep signature verification, and invokes `mach_service_identity_preview` on the staged bundle. It prints the staged app path and the exact `enabled=false` cdhash proposal; it does not save the proposal, alter the source app, install anything, enable a service, or write system configuration. The source and output paths must be absolute, disjoint, and free of symlinks and `..` components. Staging rejects symlinked bundle entries, non-empty output directories, tool errors, and timeouts. It compares paths without regard to case when checking for overlap and macOS system locations. The path checks narrow accidental path substitution but assume a trusted local filesystem; do not concurrently replace the source app or review directory while staging. Ad-hoc signing does not establish publisher identity, and the staged copy is not an installation artifact.

On macOS with Python 3, run `ctest --preset debug -R '^m6_codesign_smoke$'` after building the debug preset. The smoke test uses the system `codesign --verify -R` to evaluate the exact cdhash requirement generated by the preview CLI against the staged app. It also checks that the same staged app fails verification when given a mismatched cdhash requirement. The test stages the GUI in a temporary directory and runs offline without installing or enabling the helper.

The repository contains a review artifact at [`resources/launchd/org.local-llm-interceptor.helper.plist`](../../resources/launchd/org.local-llm-interceptor.helper.plist). Its fixed `ProgramArguments` invoke `/Library/PrivilegedHelperTools/llm_interceptor_helper --mach-service --state-dir /private/var/db/llm_interceptor`; its sole `MachServices` key is `org.local-llm-interceptor.helper`, and launchd is asked to run it as `root:wheel`. This plist is not installed, bootstrapped, or enabled by the repository tooling.

The non-installing package script checks the plist's exact keys and values, then can stage a built helper and the plist under a caller-selected review directory. For example, after a local build:

```sh
python3 scripts/package_launchd_helper.py --validate-only
python3 scripts/package_launchd_helper.py \
  --helper build/debug/llm_interceptor_helper \
  --output-dir /private/tmp/llm-interceptor-launchd-review
```

The helper input must be a non-empty regular file. Relative helper paths are interpreted from the current working directory. The staging directory must be an absolute, empty or new path outside macOS system locations. The helper and output paths must be disjoint, and both paths must be free of symlinks and `..` components. The script repeats these checks immediately before staging. Use a trusted local filesystem and avoid concurrent changes to either path during staging.

The helper is staged with mode `0755` and the plist with mode `0644`, preserving their intended relative locations under `/Library`. The script does not sign, install, bootstrap, enable, unload, or remove a service. Review the staged files before any separately authorized installation work.

On macOS with Python 3, run `ctest --preset debug -R '^m6_helper_package_codesign_smoke$'` after building the debug preset. The smoke test requires a helper with a valid embedded signature and a literal cdhash designated requirement. Linker signing output can vary by architecture. The test stages the built helper in a temporary directory, checks its embedded signature with `codesign --verify --strict`, and reads the literal requirement from `codesign -d -r-`. It passes that requirement to `codesign --verify --strict -R` on the staged copy and checks that a different cdhash fails verification. This exercises signature integrity and exact requirement matching for the staged file. The test runs as an ordinary user and leaves the source files and system configuration untouched. The target Mac's signing and provisioning decisions are tracked in the [GUI/helper trust boundary](GUI_HELPER_TRUST_BOUNDARY.md).

Before installation, review the helper's signature and ownership and provision the exact signed GUI identity as described above. The [offline A3 preflight](GUI_HELPER_TRUST_BOUNDARY.md#offline-a3-preflight) verifies the staged package and signed GUI against the reviewed cdhashes. Apply the [helper runtime dependency gate](GUI_HELPER_TRUST_BOUNDARY.md#helper-runtime-dependency-gate) before any privilege elevation.

The staged plist has not been loaded into launchd. Even with valid configuration, Mach service mode returns only read-only probe/status replies: it starts no helper host, accepts no capability, and authorizes no PF or ARP. The `--process` mode still fails closed. See [XPC control request gate](XPC_CONTROL_REQUEST_GATE.md).

The intended lab installation uses a system launch daemon, not a root GUI. The executable path is `/Library/PrivilegedHelperTools/llm_interceptor_helper`, intended to be owned by `root:wheel` with mode `0755`. Its private state directory is `/private/var/db/llm_interceptor`, owned by `root:wheel` with mode `0700`. A GUI process running as an ordinary user cannot traverse that directory to connect to a socket beneath it, so the GUI/helper rendezvous location and ownership must be designed before adding a control listener. The plist under `/Library/LaunchDaemons` is only an uninstalled artifact; installation remains gated on that rendezvous, full startup and cleanup, code-signature authentication, and gated capability handoff. Kernel UID/GID credentials alone do not prove GUI identity.

After the runtime dependency review passes and an administrator has separately staged the executable and private directory, the administrator can run the read-only state-directory check.

```sh
sudo /Library/PrivilegedHelperTools/llm_interceptor_helper --check-state-dir /private/var/db/llm_interceptor
```

The command requires effective root and checks the directory's absolute canonical path, root ownership, exact `0700` mode, stable inode, and close-on-exec descriptor. The installer remains responsible for the `wheel` group; the checker does not inspect group ownership because mode `0700` grants it no access. It prints `state_directory_ready` only after those checks. The same opened descriptor is intended for the host lease and both PF journals when the service factory is wired. This check makes no PF or ARP call and does not establish recovery readiness.

There is no supported service installation or uninstall command. The package script only creates a review directory and never loads launchd. If a future separately approved installation is removed, unload that exact service using the reviewed macOS procedure, then remove only `/Library/LaunchDaemons/org.local-llm-interceptor.helper.plist` and `/Library/PrivilegedHelperTools/llm_interceptor_helper`. Preserve `/private/var/db/llm_interceptor` until every journal and recovery obligation has been inspected and reconciled. Never issue global `pfctl -d` during uninstall.

## GUI helper identity

The administrator approves the exact cdhash of the signed helper executable selected for installation. Provision that requirement at `/Library/PrivilegedHelperTools/llm_interceptor_helper.identity`. The file contains one line of the form `helper-code-requirement=cdhash H"…"`, where the quoted value is the reviewed code signature's 40- or 64-digit hexadecimal hash. A final LF is optional. The GUI accepts the literal only if it also compiles with Security.framework.

The file must be a root-owned regular file with mode `0644`. Each ancestor directory through `/Library/PrivilegedHelperTools` must be root-owned and disallow group and world writes. The GUI rejects symlinks and extended ACLs on these components and opens them through directory descriptors. Provision a replacement as a complete file and atomically rename it into place. A helper rebuild or re-sign requires a fresh review and an updated pin. Rollback requires the matching reviewed pin for the restored executable.

The GUI reads the file when **Check helper status** is clicked. A missing or invalid file prevents any status request. A valid file enables the privileged read-only status request with the configured peer requirement. The GUI reports success after the OS verifies the peer and the response passes protocol validation. The staging scripts leave the identity file and system installation to the administrator.
