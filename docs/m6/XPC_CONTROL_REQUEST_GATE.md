# XPC control request gate

`XpcControlRequestGate` owns a copy of the trusted code requirement supplied by local configuration when the gate is constructed. For each received XPC dictionary message, it passes that exact message and pinned requirement to the injectable `XpcPeerCodeSignaturePolicy` before reading any protocol fields.

After authentication, the parser accepts exactly one dictionary key, `operation`, with a string value of `probe` or `status` (at most 16 bytes). It returns only the bounded `XpcControlOperation` enum. Extra keys, wrong value types, empty or oversized strings, and unsupported operations fail closed. The XPC message is borrowed and inspected synchronously. The injected policy must outlive the gate, and the caller must serialize `parse` calls. The gate does not encode a reply, dispatch to a host, carry a capability, or call PF, ARP, or other system operations. Start, Heartbeat, and Stop are not accepted.

`XpcReadOnlyControlAdapter` now turns only those authenticated requests into fixed replies: `probe` returns `ok`, the service label, and protocol version; `status` adds the constant state `inactive`. Rejected, malformed, or unauthenticated messages receive no reply. The payload is built from constant fields and contains no peer, network, path, or session details. The adapter accepts no Start, Heartbeat, or Stop operations.

`XpcReadOnlyServiceListener` is a reusable native XPC event listener foundation. It requires a syntactically valid service name and a nonempty trusted code requirement. It bounds concurrent peers to 16, accepted peers to 256 per run, messages to 128 per peer, and total messages to 4096 per run; reaching the run limits closes the listener. It does not install a launchd plist or derive a code identity. The listener is not wired into the GUI or helper executable, and the repository still has no installed service configuration, production identity default, GUI/helper rendezvous, capability handoff, or privileged dispatcher. A valid configured service name alone is not proof of a signed installation. This slice does not complete installed-helper acceptance or authorize PF, ARP, or other network mutation.

Offline tests cover gate authentication/rejection, fixed reply payloads, fail-closed listener configuration, and an anonymous native endpoint request/reply/stop round trip using an injected fake peer policy. They verify callback delivery through the adapter but do not verify launchd registration, real code-signature enforcement, or live enforcement of peer/request limits. Those require the signed service installation path and remain unverified.
