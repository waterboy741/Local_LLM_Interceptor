# XPC control request gate

`XpcControlRequestGate` pins the trusted code requirement from local configuration. It authenticates each actual XPC dictionary message before reading its fields. In helper Mach service mode, the Security.framework policy checks the sender's code signature using the message's kernel-bound identity.

After authentication, the parser accepts exactly one key, `operation`, with a string value of `probe` or `status` (at most 16 bytes). It returns a typed operation and rejects extra keys, wrong types, invalid strings, and unsupported operations. The gate borrows the message for synchronous inspection. The injected policy must outlive the gate, and callers must serialize `parse` calls.

The constructor-opt-in `SyntheticLifecycle` mode also parses the fixture session-control grammar specified in the [session-control contract](HELPER_SESSION_CONTROL_CONTRACT.md): `start` with `protocol_version` (uint64 1), and `heartbeat`/`stop` with `protocol_version`, a 1–48 byte ASCII `session_id`, and an exactly 32-byte `session_capability` data field — exactly four keys each. The authenticated receiver, dispatch, and reply encoding live in the lifecycle runtime fixture, not in the gate. This grammar is compiled into the system-library-only helper but is unreachable there: the installed `--mach-service` path constructs the gate in `ReadOnly` mode, so the installed service still accepts only `probe` and `status`. `XpcSessionControlReply` carries the bounded v1 reply fields (`ok`, `protocol_version`, `state`, `session_id`, the one-time `session_capability`, `reason`), and `encodeXpcSessionControlReply` enforces the field bounds and returns `nullptr` on any violation; `wipeXpcSessionControlReply` zeroes capability bytes retained by a reply.

`XpcReadOnlyControlAdapter` returns fixed fields for authenticated requests. Both replies include `ok`, the service label, and protocol version. A `status` reply adds the constant state `inactive`. Rejected messages receive no reply. This service has no session capability or Start, Heartbeat, Stop, PF, or ARP operation.

`XpcReadOnlyServiceListener` requires a valid service name and a trusted code requirement. It caps concurrent peers at 16, accepted peers at 256 per run, dictionary messages at 128 per peer, and total dictionary messages at 4096 per run. A new connection or message beyond its corresponding run cap closes the listener. The helper's root-gated `--mach-service` mode wires the listener for `org.local-llm-interceptor.helper` when explicitly enabled with a local code requirement. The launchd plist is a review artifact and there is no default trusted GUI identity. See [the helper bootstrap contract](INSTALLED_HELPER_BOOTSTRAP.md).

`XpcReadOnlyServiceClient` sends only `probe` or `status` to that fixed service and accepts only the exact reply fields and values. Each request has a 1–5000 ms deadline (1500 ms by default) and distinguishes timeout, unavailable service, connection failure, and malformed reply. The GUI's **Check helper status** button sends one `status` request asynchronously. It displays availability, the returned state and protocol version on success, or an unavailable, timeout, or failure message. An `inactive` reply confirms the read-only endpoint responded.

The existing `probe()`, `status()`, and GUI check report endpoint availability. A caller with an independently reviewed helper requirement can call `trustedStatus()` to check the helper's signing identity as well. The caller supplies one exact `cdhash H"..."` requirement. The client validates it, looks up the service in the privileged Mach bootstrap for the system LaunchDaemon, and installs the requirement on the connection before activation. Success requires both XPC peer verification and a valid status reply. Invalid requirements, unavailable or failed verifier setup, and peer identity mismatches return `InvalidPeerRequirement`, `PeerVerificationSetupFailed`, and `PeerIdentityMismatch` respectively. Trusted status requires macOS 12 or later for XPC peer verification.

Offline tests cover authentication and rejection with injected peer policies, fixed replies, configuration rejection, anonymous native endpoint round trips, deadline and error handling, exact reply validation, and GUI status handling with injected results. The trusted status tests use a signed process over an anonymous endpoint to exercise client-side XPC signing enforcement. Launchd registration, bidirectional authentication with the installed LaunchDaemon, and live enforcement of peer and request caps remain unverified.

## InstalledLifecycle enablement

The third gate mode, `InstalledLifecycle`, is constructed only by the root-gated `--mach-service` entrypoint and only when the validated `mach-service.conf` carries the exact third line `session-control=true` (see [the helper bootstrap contract](INSTALLED_HELPER_BOOTSTRAP.md)). Its `start` grammar is the 9-key installed form of the [session-control contract](HELPER_SESSION_CONTROL_CONTRACT.md) (tuple + one-time probe secret); `heartbeat` and `stop` keep the shared 4-key grammar; probe and status shapes are byte-identical in every mode. `XpcReadOnlyControlAdapter` and the new `XpcSessionControlServiceAdapter` both implement the `XpcServiceMessageHandler` responder surface consumed by `XpcReadOnlyServiceListener`, whose peer/message caps are unchanged. Status replies stay byte-identical in every mode, including the fixed `inactive` state — the reviewed read-only client accepts nothing else; lifecycle state reaches the GUI only through Start/Heartbeat/Stop replies. The GUI session-control surface is `XpcSessionControlClient`: one request at a time over the privileged Mach service, a pinned reviewed helper cdhash requirement on every call, `ok=false` replies surfaced as contract states, and wiped local secret copies. All of this is build- and injected-seam-verified only; no live LaunchDaemon exchange has been observed.
